# Migration to v3.0.0 — the portfolio brain

Applies when updating a project from any template version below v3.0.0. Run by `/template-update` after its file sync.

## What changed structurally

v3.0.0 introduced **portfolio mode**: a repo can host many projects (`projects/<name>/`, each with its own full docs brain) over a shared root layer (`standards.md` — the owner's universal taste; `portfolio_status.md` — the index). Workflows became portfolio-aware: they detect the mode by the root `portfolio_status.md` marker and scope themselves to the active project.

## Transformation rules

1. **Single-project repos: change nothing.** The toolkit files arrive via the normal file sync; without a root `portfolio_status.md`, every workflow behaves exactly as before. This migration performs **no doc or code moves**.
2. **Portfolio conversion is opt-in, owner-present, via `/add-project`** — deliberately *not* part of this migration. Reason: converting means moving code, and moving code can break builds, CI, and imports. A migration must never break a build unattended. When the owner is ready, `/add-project` runs the conversion interactively, with the build proven green afterward.
3. Tell the owner, once, in the update report: *"This version adds portfolio mode — if this repo hosts (or will host) more than one project, run `/add-project` when you have twenty minutes; nothing changes until you do."*

## Convention for all future migrations

From v3.0.0 on, every migration file must state whether it applies **per-project** in portfolio repos (run once per `projects/<name>/docs/` brain) or repo-level. Doc-structure migrations are per-project by default.

## Zero-loss verification

File-sync only — the standard three-way rules apply; no project content is touched by this migration.

## Verify

Run the validator if present; confirm single-project workflows behave unchanged (no root `portfolio_status.md` → classic mode).
