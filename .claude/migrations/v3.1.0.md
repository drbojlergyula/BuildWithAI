# Migration to v3.1.0 — the evidence layer

Applies when updating from any version below v3.1.0. **Per-project** in portfolio repos (once per `projects/<name>/docs/`). Run by `/template-update` after its file sync; execute via the `builder`; verify with `doc-sync-check`.

## What changed structurally

v3.1.0 added an `## Engineering Profile` section to `docs/project_spec.md` (see `.claude/rules/engineering.md`). Older projects have no profile, so their changes cannot be classified by risk and their verifier runs no gates.

## Transformation rules

1. **Add the profile — by inference, not interview.** Read the existing spec, architecture, house rules, and decisions; fill the ~10 profile lines from what they already say (exposure, sign-in, data, money, uploads, integrations, scale, loss tolerance, regulated). Where a line is genuinely unknowable *and* risky *and* would change what gets built, leave it marked `to confirm` — do not ask during a migration; the next `/new-feature` touching that area asks once, per the three-condition rule.
2. **Detect the proof command.** Look for the project's test/check command (`package.json` scripts, `pyproject`/`Makefile`/`justfile`, CI workflows). Record it, or `none yet`.
3. **Change nothing else.** No gates run retroactively; no reclassification of past work. The layer applies from the next change onward.

## Zero-loss verification

Additive only: the spec gains one section; no line of existing content moves or changes. Report: profile added (lines inferred / marked to-confirm), proof command found or `none yet`.

## Verify

`doc-sync-check` — the profile matches what the code actually does (a profile saying "no sign-in" while an auth module exists is drift, flagged).
